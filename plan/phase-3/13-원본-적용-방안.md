# 13. 테스트 정리 · 원본 파일 적용 방안 (2026-11-17)

사용자: "테스트는 여기까지만 하는 것으로 하고, 지금까지 디자인시스템 적용했던 부분을 정리해서, 지금처럼 복사본 파일이 아닌 원본파일에서도 적용할 수 있도록 방안을 마련해줘."

사용자(이어서): "원본 파일이 지금 계속 추가되고 있는 상황이라서, 여기서 멈추는거야."
→ 이 때문에 달라지는 것(AI 의견): ① 길 B(복사본을 원본으로)는 못 씀 — 복사 뒤 원본에 더해진 것이 사라짐. ② 원본용 도구는 부품 번호가 아니라 이름으로 찾아야 하고, 분류표에 없는 새 부품은 "분류 안 됨"으로 따로 모아 보고해야 함. ③ 원본 작업은 추가가 잦아드는 때에 하고, 하는 동안에는 부품 페이지를 다른 사람이 고치지 않게 해야 함(같이 고치면 옮기는 중에 어긋남). ④ 그 전까지는 새 부품을 만들 때 2번 규칙만 미리 지켜도 나중 일이 줄어듦.

테스트 파일: `jey6PXIFB19gl5et1XzIzi`(와이즈 컴포넌트 테스트, 복사본). 아래 "방안"은 모두 AI 의견이고, 실행은 사용자가 "진행"이라 할 때.

## 2. 테스트에서 정해진 규칙 (원본에도 그대로 쓸 것)

사용자가 정한 것
- 큰 틀은 KRDS(시작하기 / 디자인 스타일 / 컴포넌트 / 패턴), 부품 분류는 Ant Design 6묶음. 저장값은 안 바꿈.
- name 종류 칸 값 = 부품 이름(빗금이 있으면 마지막 토막).
- 오타는 고침. 이름만 같고 다른 부품은 패턴 쪽 이름을 바꿔 구분.
- 부품 모습: 가로 = 사이즈, 세로 = state, 줄·칸 이름표 붙임(버튼).
- 입력폼: type 별 묶음. 상태 순서 default · hover · focused · typing · typed · disabled · error.
- show-chip 묶음처럼 default 가 기본 상태와 같아 없는 경우도 나머지는 같은 순서.

AI 가 정한 것(원본 적용 전 한 번 봐 주실 것)
- 아이콘·로고 54개는 문서 한 장(목록)으로.
- 사이즈가 없는 부품은 가로 칸을 다른 종류 칸으로.
- 선택 쪽 상태 순서(unchecked · unselected · checked · selected · active · partial, disabled · error 는 맨 뒤).
- 격자가 틀보다 넓으면 상태별 줄바꿈 나열.
- service-tag 의 `type=ipo` 값 이름.

## 3. 원본에 옮기는 길 3가지

| 길 | 방법 | 좋은 점 | 걸리는 점 |
|---|---|---|---|
| A. 원본에서 단계별로 다시 실행 (추천) | 테스트에서 한 일을 같은 순서로 원본에 다시 함. 단계마다 확인 | 원본 주소·화면 연결·개발 쪽 링크가 그대로. 단계마다 멈출 수 있음 | 다시 실행하는 시간이 듦 |
| B. 복사본을 새 원본으로 삼기 | 테스트 파일 이름을 바꿔 원본으로 씀 | 다시 할 일이 없음 | 파일 주소가 바뀜(개발 쪽 링크 · 댓글 · 버전 기록이 옛 파일에 남음). 복사한 뒤 원본에서 고친 것이 있으면 사라짐 |
| C. 복사본에서 페이지를 복사해 붙이기 | 문서 페이지를 원본에 붙여 넣기 | 문서만 빨리 옮김 | 붙인 문서 속 부품이 원본 부품이 아니라 복사본 부품에 걸림. 구조·이름 정리는 안 옮겨짐 |

AI 의견: A. B 는 원본이 계속 추가되는 중이라 뺌. 이유 — 서비스가 이미 개발돼 있어 파일 주소와 화면 연결을 지키는 것이 가장 중요하고, 이름 바꾸기처럼 개발에 영향이 있는 일은 시점을 따로 잡을 수 있어야 함.

## 4. A 길 — 실행 순서

### 0단계. 준비 (읽기만)
- 원본이 어느 파일인지 확정(파일 주소 받기).
- 원본과 복사본 비교: 부품 수(공통 132 · 패턴 139 였음), 부품 이름 목록, 구역 이름. 복사 뒤 원본에서 바뀐 것이 있으면 표로 보고.
- 피그마 버전 기록에 "디자인시스템 구조화 전" 이름으로 저장(사용자가 직접 — 되돌릴 자리).
- 원본이 라이브러리로 내보내져 다른 파일에서 쓰이는지 확인. 쓰이면 이름 바꾸기 뒤 다시 내보내야 함.

### 1단계. 구조 (개발 영향 없음)
- ㄱ 그대로: 6묶음 구역 만들기 → 패턴·공통 부품 옮기기 → 꼬리표 → 옛 구역 보관.
- 확인: 부품 수 그대로, 구역 겹침 0, 끊긴 인스턴스 0.

### 2단계. 이름 정리 (개발 영향 있음 — 시점은 사용자·개발 쪽이 정함)
- 먼저 개발 쪽에 바뀔 목록 전달: 부품 이름 8개, 종류 칸 이름 7곳, name 값 맞춤 목록, service-tag type=ipo.
- ㄴ → ㄷ → ㄹ → ㅁ 순서로 실행. 묶음 하나씩이 아니라 한 번에 하되, 실행 전 "바꿀 표"를 보여 드리고 승인받음.
- 확인: name 값 어긋난 묶음 0, 같은 이름 묶음 0, 화면 쪽 끊긴 인스턴스 0(테스트에서는 화면 쪽을 하나씩 안 봤음 — 원본에서는 화면 페이지 전체를 숫자로 점검).
- 이 단계는 1단계와 떼어서 나중에 해도 됨.

### 3단계. 문서 (개발 영향 없음)
- 시작하기 페이지 · 부품 설명 틀 만들기.
- 부품 설명 페이지: 처음부터 2번 규칙(격자 · type 묶음 · 상태 순서 · 이름표)으로 만듦 → 테스트처럼 만든 뒤 다시 놓는 일을 줄임.
- 테스트에서 사용자가 손으로 적은 내용(사용 규칙 등)이 있으면 그 글자는 복사본에서 읽어 옮김.
- 확인: 문서 수, 틀 밖으로 나간 부품 0, 묶음마다 2~3장 화면 캡처.

### 4단계. 마무리 (사용자)
- 서체 바꾸기 플러그인(Noto Sans KR → Wanted Sans).
- 빈칸 채우기: 사용 규칙, 패턴 부품 용도 한 줄, 뜻을 안 적은 상태.
- 테스트 파일은 지우지 않고 이름 앞에 `[테스트 끝]` 을 붙여 둠.

## 5. 다시 쓸 도구
- 테스트 때는 그때그때 짠 것이라, 원본용은 부품 번호가 아니라 **이름으로 찾는** 방식으로 다시 짜서 `scripts/` 에 단계별로 둠(원본과 복사본의 부품 번호가 같은지는 확인 안 함 — 0단계에서 확인).
  - `scripts/ds-01-구조.js` · `ds-02-이름정리.js` · `ds-03-문서.js` · `ds-00-점검.js`(읽기 전용, 단계 앞뒤로 실행)
- 6묶음 분류표는 03번 문서를 그대로 씀. 원본에 새 부품이 있으면 0단계 비교표에서 따로 분류.

## 6. 사용자가 정할 것
0. 원본 작업을 언제 할지(추가가 잦아드는 때). 그때까지 새 부품에 2번 규칙을 미리 쓸지.
1. 원본 파일이 어느 것인지(주소).
2. 길 A · C 중 어느 것(B 는 뺌).
3. 2단계(이름 정리)를 1 · 3단계와 같이 할지, 개발 쪽과 날짜를 맞춰 따로 할지.
4. 2번의 "AI 가 정한 것" 5가지를 원본에도 그대로 쓸지.

## 7. 테스트에서 안 끝난 것 (원본에서 이어질 일)
- 격자·묶음 정렬은 버튼 8 · 입력 3 · 선택 17장만. 나머지 185장은 줄바꿈 나열.
- 넓은 선택 4장(box-date-select · box-text-select · dropdown-ui-list · input-select)은 격자가 아님.
- ` menu-ui-icon` 이름 앞 빈칸, `charge-type` 의 칸 이름 `Property 1`.
- 사용 규칙 213장 빈칸, 용도 한 줄 135장 빈칸.
- 화면 캡처로 본 문서는 20장 안팎(어림값). 화면 쪽 인스턴스는 하나씩 확인 안 함.
